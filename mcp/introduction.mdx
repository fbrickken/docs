## Overview

The Brickken MCP server exposes the Brickken Dapp API and Agentic API as 63 tools for MCP-compatible AI agents.

It is **the client to reach for when an AI agent should drive the full Dapp API with nothing but an API key**, including KYC link creation. If your own code is driving rather than an agent, use the [SDK](/sdk/introduction). See [Choose your surface](/get-started/choose-your-surface).

## Connect

The hosted endpoint requires your Brickken API key. Send it in the `x-api-key` header or as `Authorization: Bearer <api-key>`. Don't have a key yet? [Request an API key](/get-started/request-api-key).

Note the `/mcp` path — the bare host serves an HTML landing page, not the MCP endpoint.

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http brickken https://mcp.brickken.com/mcp --header "x-api-key: YOUR_API_KEY"
    ```
  </Tab>

  <Tab title="Cursor and JSON clients">
    ```json
    {
      "mcpServers": {
        "brickken": {
          "url": "https://mcp.brickken.com/mcp",
          "headers": {
            "x-api-key": "YOUR_API_KEY"
          }
        }
      }
    }
    ```
  </Tab>

  <Tab title="Claude Desktop (stdio)">
    Clients that only support stdio servers connect through `mcp-remote`, with the key kept in `env`:

    ```json
    {
      "mcpServers": {
        "brickken": {
          "command": "npx",
          "args": [
            "-y",
            "mcp-remote",
            "https://mcp.brickken.com/mcp",
            "--header",
            "x-api-key:${BRICKKEN_API_KEY}"
          ],
          "env": {
            "BRICKKEN_API_KEY": "YOUR_API_KEY"
          }
        }
      }
    }
    ```
  </Tab>
</Tabs>

A request without a key is rejected with `401`:

```text
Authentication required. Connect your Brickken sandbox or production account: send your Brickken API key in the x-api-key header or as Authorization: Bearer <api-key>.
```

A key that Brickken does not recognize is rejected with `401` and `The API key is not valid for Brickken sandbox or production.`

## Environment

Your API key selects the environment: a sandbox key opens a sandbox connection, a production key a production connection. Sandbox and production keys are separate — see [Authentication](/get-started/authentication).

Use `configure` to switch `env` between `sandbox` and `production`. The switch is accepted only when your connected API key is valid in the target environment. The API key itself always comes from the connection header; `configure` does not accept `apiKey` or `privateKey`.

<Note>
Brickken never receives a private key. The MCP server never signs: every write tool returns unsigned transactions, you sign them in your own wallet, and only signed transactions are sent to Brickken.
</Note>

## Configuration Tools

| Tool | Purpose |
| --- | --- |
| `configure` | Switch `env` (`sandbox` or `production`) for the current connection. |
| `get_config` | Inspect `env`, `baseUrl`, `hasApiKey`, and `hasPrivateKey`. It returns booleans, never secret values, and `hasPrivateKey` is always `false`. |

## Signing writes

Every write tool follows the same flow:

1. **Prepare.** The tool returns unsigned transactions and a `txId`.
2. **Sign in your wallet.** Sign each prepared transaction with the wallet named in `signerAddress`. When the response includes a `signUrl`, open it to sign in your wallet.
3. **Send.** Call `send_transactions` with the `txId` and the signed transaction(s). Brickken broadcasts them.

The signer wallet must be whitelisted by Brickken before a write is accepted, and your key can only act on token symbols it tokenized. See [Authentication](/get-started/authentication).

<Tip>
For automatic signing or x402 pay-per-call without an API key, keep your private key in your **local** environment (`BRICKKEN_PRIVATE_KEY`) and use the [CLI](/cli/introduction) or the [SDK](/sdk/introduction). Both sign on your machine; the key never leaves it.
</Tip>

## BKN Faucet Tool

`request_bkn_faucet` requests 100 BKN on Ethereum Sepolia in Sandbox. Pass `recipientAddress` and optionally `idempotencyKey` as UUID v4. The tool generates and returns a UUID when omitted; use a new UUID for a new claim and the same UUID for a retry of that claim.

Each API key has 10 dedicated lifetime faucet claims, separate from `mintToken`. Recipients have a 24-hour cooldown. The public bearer/reCAPTCHA flow is not exposed.

## Transaction Tools

| Tool | Purpose |
| --- | --- |
| `prepare_transactions` | Prepare unsigned transactions for a backend `method`. |
| `send_transactions` | Submit signed transactions to Brickken. |
| `get_transaction_status` | Poll a transaction hash. |

## Dapp API Tools

These tools map to API-key authenticated dapp flows and are **the legacy Dapp API, reachable from an AI agent with nothing but an API key**. Write tools return prepared, unsigned transactions; sign them in your wallet and submit them with `send_transactions`.

| Area | Tools |
| --- | --- |
| KYC | `create_kyc_link` |
| BKN faucet | `request_bkn_faucet` |
| Tokenization | `create_tokenization` |
| STOs | `create_sto`, `invest_in_sto`, `claim_sto`, `close_sto` |
| Security-token operations | `mint_tokens`, `whitelist_investor`, `burn_tokens`, `transfer_tokens`, `approve_tokens`, `distribute_dividend` |
| Reads | `get_network_info`, `get_token_info`, `get_tokenizer_info`, `get_stos`, `get_sto_by_id`, `get_investments_by_sto_id`, `get_investor_info`, `get_allowance`, `get_whitelist_status`, `get_balance_whitelist`, `get_sto_balance`, `get_dividend_info` |

<Warning>
`create_kyc_link` can create an investor account and send an invitation email. Treat its returned Sumsub URL as sensitive.
</Warning>

## Agent Tools

These tools map to ERC-8004 and agent-token methods on Base, plus RAMS mandates. They use your API key and follow the same prepare → sign in your wallet → send flow.

| Area | Tools |
| --- | --- |
| Agent reads | `get_agents`, `get_agent_info`, `get_agent_transactions` |
| Agent identity | `agent_register`, `agent_set_uri`, `agent_set_metadata`, `agent_set_wallet`, `agent_transfer_ownership` |
| Reputation | `agent_give_feedback`, `agent_revoke_feedback`, `agent_append_feedback_response` |
| Agent-owned tokens | `agent_create_token`, `agent_mint_token`, `agent_burn_token`, `agent_transfer_token`, `agent_transfer_from_token`, `agent_approve_token` |
| RAMS mandates (ERC-8226) | `rams_grant_mandate`, `rams_revoke_mandate`, `rams_extend_mandate`, `rams_set_operator`, `rams_execute`, `rams_set_executor_action`, `rams_freeze_agent`, `rams_unfreeze_agent`, `rams_grant_principal`, `rams_revoke_principal`, `rams_get_mandate`, `rams_can_execute`, `rams_get_status`, `rams_check_compliance`, `rams_get_executor_action`, `rams_get_typed_data` |

`rams_get_typed_data` returns the EIP-712 envelope for a signed lifecycle operation. The principal signs it in their own wallet; pass the resulting signature and deadline to the matching lifecycle tool.

Agent detail and transaction reads accept `agentUuid`, or `agentId` together with `chainId`.

## Networks

Use `chainId: "8453"` for Base mainnet and `chainId: "84532"` for Base Sepolia tests (decimal or hex accepted).

## Execution mode

Agentic write tools use `client-signed` execution: provide `signerAddress`, sign the prepared transaction in your wallet, and submit it with `send_transactions`. Brickken broadcasts it. See [Pricing](/api-reference/endpoint/agentic-pricing).

<Note>
  If you would rather not hold an EOA or native gas at all, see [Base MCP](/mcp/base-mcp), where the
  wallet only authorizes the payment and Brickken carries the signing and the gas.
</Note>

## Example

Connected with a sandbox API key, register an agent on Base Sepolia with `agent_register`:

```json
{
  "chainId": "84532",
  "signerAddress": "0x1111111111111111111111111111111111111111",
  "name": "Research Agent",
  "description": "On-chain AI research agent",
  "image": "https://example.com/agent.png",
  "serviceName": "A2A",
  "serviceEndpoint": "https://agent.example/.well-known/agent-card.json",
  "aiModelProvider": "OpenAI",
  "aiModelName": "Research Model",
  "x402Support": true,
  "active": true
}
```

The `agent_register` result contains the unsigned transaction and its `txId`. Sign it with the `signerAddress` wallet (or open `signUrl` when present), then call `send_transactions` with the `txId` and the signed transaction. Save `info.agentUuid` for later agent updates, including `agent_transfer_ownership`.
